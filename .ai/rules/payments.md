# Payments

## A return is read for a reference and nothing more; a Verification decides
`PaymentController::processing()` reads the gateway's return through `paymentReferenceFromReturn()` and writes only the gateway's reference onto the Payment. Whatever the return says about the outcome — SSLCommerz posts `status=VALID` beside it — is never believed (ADR-0013). The state changes in exactly one place, `PaymentVerifier::verify()`, and only for a Pending Payment: the gateway is asked outside any lock, then the outcome is written under the Order's lock against a fresh read, so the Processing Page, a Notification and the sweep verifying at once produce one write and never two Paid Payments. A settled Payment (Paid, Failed, Cancelled, Expired) is not asked about again, which is what makes a refresh of the Processing Page and a second call of the verification endpoint free.

A driver's `verify()` takes the Payment, not a reference, because the reference is not always there. SSLCommerz sends a Customer who cancelled back with no `val_id`, so `SslCommerz::verify()` asks the validation API by `val_id` where the Payment holds one and the transaction query API by our `tran_id` otherwise — that is the only way a Cancelled state is ever reached honestly. Paid needs three things to agree: the status says taken, the answer names this Payment's invoice reference, and the amount and currency taken are the Payment's own. The `val_id` arrived on an unauthenticated POST to a guessable address, so an answer that does not name this Payment — `INVALID_TRANSACTION`, or someone else's transaction — settles nothing: the driver falls through to the query by our `tran_id` and decides on that. Do not "simplify" that into Failed; it would let a forged return pin a real Payment Failed before the Customer's own return arrives. The gateway's own `EXPIRED` maps to the Expired state; only a taken status with the wrong amount or the wrong reference is Failed.

## Could not start is Failed on the record and never an exception to the Customer
`PaymentStarter::start()` creates the Pending Payment for the Order's total *before* asking the gateway, under the Order's lock so the invoice reference (`{order number}-{attempt}`) is never reused. A driver that cannot reach or is refused by the gateway throws `PaymentNotStarted` carrying what was said; the starter marks the Payment Failed with that, and answers null, which `CheckoutController::sendOn()` turns into the Retry Page. Starting is refused without a call when the method is not online, has no driver, or is not among `Order::retryPaymentMethods()` — so a method the Page lists but can no longer offer captures Unpaid with no Payment, and no gateway is spoken to for it.

The start call fills every mandatory field from the Order and puts a fixed placeholder where the Checkout never asked (`SslCommerz::PLACEHOLDER_*`). The Checkout does not grow a question for a gateway's sake; a blank refused by the gateway would be a Customer turned away for a question the Merchant chose not to ask.

## The edges of the axis are rules on the record, not exceptions to the Customer
`PaymentStarter::start()` refuses to start while another Payment on the Order is Pending and younger than `Payment::RETRY_WAIT_SECONDS` (about a minute), checked under the Order's lock by `Order::recentPendingPayment()` so two taps a second apart cannot both start one. This is the one refusal that throws — `PaymentStillPending`, worded for the Customer — because it is the one with something to say: `CheckoutController::sendOn()` catches it and lands on the Retry Page with the reason beside the chooser. Switching to Cash on Delivery is not starting a Payment and is never held off. An Order already Paid starts nothing more, whatever a stale Retry Page posts.

A second Payment that verifies Paid is recorded Paid as it is — money moved, and the record says what happened — and `PaymentVerifier` flags the Order on its own activity trail with the event `paid_twice` naming both invoice references; `Order::isPaidTwice()` reads it. Do not turn the second into Failed or Cancelled to keep "at most one Paid" true: a refund is the operator's, and it needs the evidence. Likewise a Payment that verifies Paid against a Cancelled Order stays Paid and the Order stays Cancelled; nothing in the payment code reads or writes `status`.

`CheckoutConfig::acceptedMethods()` is every known `PaymentMethod`, not the Page's list: a Merchant reorders, toggles logos on or removes a method from the tab under live forms, and at Capture a removed method cannot be told from one never listed, so any known name is taken and captures Unpaid with no Payment (the Retry Page then offers what the Page offers now). Only a name that is no method at all is refused. Do not narrow this back to the Page's list; it turns a Merchant's edit into a refused Customer.

## The gateway is one seam, and every test fakes it
Every driver speaks through the framework's HTTP client with a short timeout, and `tests/Pest.php` calls `Http::preventStrayRequests()` before every feature test. A test that captures under a usable online method without a fake used to reach the real sandbox, wait out the timeout, and pass on the Failed Payment the outage produced — which is why `RetryPageTest` fakes an outage to make an Unpaid Order. `OnlinePaymentTest` runs as a dataset over `tests/Fixtures/Payments/GatewayScript`, one script per gateway holding its documented shapes; a new gateway is a new script and a new row, never a new test file. A script's verification fakes are closures matched on the reference in the request (`val_id`, `tran_id`), not on the address alone, and `gatewayReference()` is per Payment: `Http::fake()` stacks and the first callback to answer wins, so address-only fakes for two Payments on one Order would have the first Payment's answer shadow the second's.

## A Notification finds a Payment and never decides about one
`PaymentController::notify()` is one address per online gateway (`/pay/{method}/notify`), registered *before* the Processing Page route so `notify` is never read as an invoice reference. The driver's `readNotification()` turns the request into a `Notification` — our invoice reference, the gateway's reference where it carries one, and the figure it claims — and the controller uses that to find the Payment and to refuse a hint that disagrees with the record. Nothing the Notification says of the outcome is read; `PaymentVerifier::verify()` decides, exactly as it does from the Processing Page. The Payment is found by *our* reference, not the gateway's, because the case the endpoint exists for is the Customer who never came back — that Payment holds no `gateway_reference` yet. The reference the Notification carries is **lent** to the Verification on the in-memory model and never saved: it came from a guessable address, and a bogus one written down would cost every later Verification a second call and show the operator a reference the gateway never issued. What the record takes is the `val_id` the gateway itself names in its answer, which is why `SslCommerz::verifyByValidationId()` hands it back on the `Verification`. (The Processing Page still writes the return's reference first, as `.ai/rules/payments.md` above records; that is #69's decision and untouched here.)

It answers 200 for everything except a method with no driver or under another method's path: a gateway that is not answered 200 retries, and there is nothing to retry for a Notification naming no Payment or the wrong amount. Those two are logged at warning with what they named and claimed — never the whole body, which carries card details — and not asked about. A Verification that throws is reported and still answered 200: a retry from the gateway would fail the same way, and the sweep asks again regardless. The route is throttled per address (`payment-notification`) because it is unauthenticated and costs a call to the gateway; a refused gateway retries, so nothing is lost but time.

## The sweep asks by age, and Expired is written under the same lock as Paid
`PaymentSweep` reads two ages off `created_at`: a Pending Payment older than `RECHECK_AFTER_SECONDS` is verified again, and one older than `EXPIRE_AFTER_SECONDS` goes through `PaymentVerifier::verifyOrExpire()` — one final Verification whose answer wins if it gives one, then Expired only if still Pending, written under the Order's lock against a fresh read like every other outcome. Do not mark Expired without the Verification first: a Payment a day old that the gateway says was taken is Paid, late. Nothing younger than the recheck age is touched, because the Customer may still be on the gateway's page and the Processing Page will ask. Expired blocks nothing: `Order::recentPendingPayment()` looks only at Pending, so the Retry Page starts the next attempt as it would after Failed.

Note for the test scripts: a fake that *throws* (`fakeOutage`) is never recorded by the HTTP client, so `assertSentCount()` cannot prove an outage was asked — assert on `verification_response` instead, which the verifier writes for a Pending answer too. And `Http::fake()` stacks with the first answering callback winning, so an outage fake shadows every fake registered after it; a test that must start a Payment after giving up on one uses `fakeVerifiedStillPending()`, which is matched on the reference and answers nothing else.

## The Processing Page and its verification sit outside request-forgery protection on purpose
A gateway sends the browser back with a cross-site POST carrying no session and no token, so both routes drop `PreventRequestForgery` and take GET as well as POST. The verification endpoint answers JSON to the page's script and a 303 to a client without one (the meta refresh), and both routes 404 a Payment under another method's path (`PaymentController::abortUnlessUnder()`). Nothing on either page names the Customer; the invoice reference is the only thing about the Order printed, because this is the one address a gateway's own logs hold.

## Every settled outcome is written on the Order's trail, once, by whoever settled it
`Payment::logOutcome()` writes a `payment_{state}` activity entry on the *Order* (never on the Payment) with the invoice and gateway references and the amount; the Order is the trail an operator reads on the call. It is called from exactly the places a Payment leaves Pending: the write `PaymentVerifier::verify()` hands to `settle()` after a Verification records Paid/Failed/Cancelled/Expired, `verifyOrExpire()` after Expired, and `PaymentStarter::start()` after a refused start marks Failed. A still-Pending answer logs nothing — Pending is not an outcome. The causer is `auth()->user()`, so a check from the admin names the operator and one from the Processing Page, a Notification or the sweep names nobody; `RetryPageTest` and `OrderPaymentsAdminTest` assert on `event`, so do not rename the events without them.

## bKash asks by the create's payment id, executes only on a success return, and settles nothing on an answer that names another invoice
bKash has no query by our invoice reference, so `Bkash` asks every question by the `paymentID` the create answered, kept in `start_response`; the return's id is written as `gateway_reference` only when the return's `status` is `success`, and is read as "the Customer came back", never as the id to ask by. A failure or cancel return yields no reference on purpose: executing it would take money nobody authorised, so the status query answers for those (Pending until bKash says `2069` cancelled or `2002` invalid, or the sweep expires it after bKash's own day). `verify()` executes when `gateway_reference` equals the create's id and no earlier Verification recorded a refused execute under `verification_response['execute']` (carried forward onto every later Pending answer by `keepingRefusedExecute()`, since the verifier overwrites the record); an execute answer that is refused, already completed, or names another invoice settles nothing and falls through to the status query, kept beside it under `execute`. Completed naming another invoice is Pending, not Failed, because the question was asked by our own id. The grant token is cached under `bkash:grant-token:{sha1(host|appKey|username)}` for `TOKEN_TTL_SECONDS` and refreshed at most once per call on HTTP 401, because bKash allows two grants an hour; `BkashDriverTest` counts grants, so an `Http::fake()` laid later never answers before one laid earlier — flip a flag inside one fake instead. The webhook is an SNS envelope (JSON under text/plain; `Message` is a JSON string naming `merchantInvoiceNumber`), the Notification lends no gateway reference (its `trxID` is not the payment id), and a `SubscriptionConfirmation` is visited only on an `sns.<region>.amazonaws.com` https address.

## aamarPay has one question, by our reference, and the return's id is never asked by
aamarPay's transaction check (`/api/v1/trxcheck/request.php`) is asked by the merchant's own transaction id and nothing else, so `AamarPay::verify()` asks by `invoice_reference` whatever the Payment holds: the `pg_txnid` off a return is written as `gateway_reference` only to say the Customer came back, and there is no second question to fall through to when an answer names another Payment — the one answer, by our reference, is the one settled on. The shared dataset counts the questions a driver asks past a foreign reference through `GatewayScript::questionsToSettlePastAnotherReference()` (two by default, one here); do not hard-code two in a shared test. Paid needs status code `2`, `mer_txnid` naming this Payment and `amount`/`currency` matching; `3` is Expired and `7` is Failed; aamarPay names no code for a cancelled Customer, so a `pay_status` opening with "Cancel" is read as Cancelled ahead of the code. The Verification hands `pg_txnid` back only when Paid, so a Failed answer on a reference lent by a Notification writes nothing down. The start is a JSON post to `/jsonpost.php` answered by `result: "true"` (a boolean is taken too) and `payment_url`; the refusal shape is undocumented, so `reason()` reads the usual keys and falls back to the HTTP status. The IPN is the return's fields posted for a taken Payment only, registered once through aamarPay's support desk, and the Settings section prints that URL.
