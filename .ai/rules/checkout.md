# Checkout

## Styling is a token set, never a generated rule
The island's CSS is flat, single-class and prefixed so that a merchant's own stylesheet overrides it without raising specificity — that is a promise the product makes, not an accident of how the block was written. A generated `.gio-checkout-field-3 { … }` would be more specific than the hand-written rule beside it on the same page, so the style editor would start winning arguments it is supposed to lose.

So everything a merchant can restyle is a custom property in `StyleToken`, declared once on `.gio-checkout` and read by the rules that were already there. There are exactly eleven — accent, text, muted, border, surface, background, radius, font, and the button's background, text and radius — and they are set once, on the Look tab, for the whole checkout and every layout alike. Nothing generates a selector, which is why the emitted block is the same bytes on a checkout asking twenty questions as on one asking two. If you find yourself wanting a new rule to express an appearance setting, add a token instead — and if it cannot be a token, it is asking for CSS the merchant should write.

**No single question restyles itself.** A field once carried a `style_tokens` set of its own, emitted as an inline `style` on its wrapper; that is retired (#86). `CustomCheckoutField::fromArray()` and `BuiltInCheckoutField::fromArray()` do not read the key, `toArray()` does not write it, and the view writes no `style` attribute on a field wrapper — `ignores a question's stored appearance and writes no style on its row` pins all three. Do not bring the box back on a question row, and do not pair the inherited properties (`color`, `accent-color`) on `.gio-checkout-field` again: that repetition existed only so a per-field redeclaration could reach them, and with nothing redeclaring below the root it is dead weight.

**A stored `background` with no `surface` beside it is read as `surface`.** The old `background` filled the inputs; that is `surface` now, and `background` paints the ground behind the card (default the design's grey `#f7f8fa`; `transparent` lets the page through). `StyleTokens::fromArray()` moves the lone key over so a published Page keeps the boxes it coloured rather than gaining a slab behind the form on upgrade; a Config storing both is read as it says, and the first save writes the new shape. Same pattern as `order_button` under `words`, and the one place the old meaning is still read.

**A retired token is dropped on read, not migrated.** `StyleTokens::fromArray()` is total, so a Config still storing `max_width`, `border_width`, `input_size`, `font_size`, `error` or `selected` reads as if it never had — the figure each once carried is now written in the sheet: the form sits at `30rem`, borders are `1px`, the type is `1rem`, a refusal is written in `#b91c1c`, and the picked state reads the accent directly. Adding one of these back as a token is a decision for a ticket, not a convenience for a rule that wants a knob.

**The font is a token and the face is shipped with the app.** `CheckoutFont` owns Hind Siliguri: the woff2 files under `public/fonts/hind-siliguri` (four weights, each split by script as the service splits them), the `@font-face` block, and the default stack the token names it in. `StyleTokens::fontFaces()` emits the block once, at the top of the base sheet, and only while the font in force names the family — `inherit` is the page's own typeface and gets no face, and so does a stack of the merchant's own. `StyleTokenKind::Font` accepts bare, unquoted family names separated by commas, or `inherit`, and nothing else: quotes are refused so a value survives Blade's escaping into the `<style>` block, and the CSS-wide keywords (`initial`, `unset`, …) are refused by name because each is one bare word the family pattern would otherwise take. The order complete page does not read the font token — it is our own document and loads nothing from anywhere — so its `font-family` stays a system stack.

## A fixed modifier class is not the generated rule the token set exists to avoid
The rule above says an appearance setting becomes a token rather than a rule. Two things are deliberately not tokens, and neither breaks it.

**A layout is a class on the root, and every layout adds to one shared sheet.** There are ten, in the design's order — Stacked, Split, Split reversed, Stepper, Accordion, Bento grid, Compact embed, Chips, Invoice, Dark panel — and the base is common to all of them; the base *is* Stacked as designed (#89), and a layout whose own block has not landed yet draws as the base does under its own class. What differs is a small additive block emitted *only* when that layout is the one chosen (ADR-0009). `CheckoutLayout::fromStored()` reads the first layouts' names — `compact` as Compact embed, `summary_first` as Split reversed — in one private map; do not read those names anywhere else. Whether the Product List is drawn is **not** a layout: it is `CheckoutConfig::showProducts`, a switch that works on any arrangement, and the view omits the panel rather than hiding it by a rule. `form_only` was once a fifth layout that meant exactly that switch; it is retired (a private constant on `CheckoutConfig`, the one reader), and a Config still stored under it reads as stacked with `show_products` false — never as stacked with the panel back, which would change a published page on upgrade. Do not add the case back, and do not read the retired name anywhere but `CheckoutConfig::fromArray()`.

How wide the form sits is not a token: it is the design's figure, written in the base on `.gio-checkout-card` as `max-width: 35rem` (the handoff README's 560px). A layout that wants a different width states its own in its additive block; it does not reintroduce a width token to do so.

The rule this is most often confused with still stands, so read it before "simplifying" the emission back: **a layout may not carry a sheet of its own.** The block rides inside every cached page, so ten copies of the base would charge every visitor ten times for the one arrangement they are looking at. An additive block that appears only when it applies charges nobody — which is why `LandingPageTest` pins two things where it used to pin one: the base is identical across all ten, and a page contains no other layout's rules (matched as a whole class, because `gio-checkout-split` is the start of `gio-checkout-split-reversed`). A test asserting the emitted styles are byte-identical *between* layouts is the old invariant and was correct only while no layout added anything; do not restore it.

**Every predicate on `CheckoutLayout` is an exhaustive match over all ten**, and the view and the tab read the same one: `wordSlots()`/`draws()`, `drawsDeliveryDetail()`, `drawsShortPaymentLabels()`, `pairsQuestions()`, `behaves()`, `defaultButtonWording()`, `thumbnail()`. Adding a case means answering every question before anything draws it; a `default` arm would let a layout draw wrong with nothing failing. Read a predicate through `LayoutChoice::selected()` on the tab, never `checkout_config.layout` directly.

**The quantity stepper is `.gio-checkout-quantity-stepper` / `.gio-checkout-quantity-step`, not `.gio-checkout-stepper`.** The Stepper layout's modifier class is `gio-checkout-stepper`, and `ships no other layout's rules` reads the sheet for every other layout's class; a component class equal to a layout's class fails that test on nine pages. Name a component class so that no layout's modifier (`gio-checkout-<layout>`) is a whole-word match for it.

**A field's width is a flat class too, and its breakpoint cannot be a token.** `.gio-checkout-field-half` is in the base sheet whether or not any question uses it, so pairing every question costs the same bytes as pairing none, and it beats `.gio-checkout-field` by order rather than by specificity — the same trade the quantity stepper makes. The two-column grid exists only inside the media query, which is the whole of "the collapse on a phone cannot be overridden": there is nothing to override, because no per-page value reaches it. A custom property cannot be read in a media-query prelude, so a per-page breakpoint would have to be a generated rule — the thing the token set exists not to do. Compact embed and Split reversed pair nothing (`pairsQuestions()`): the view writes no half class on a page arranged in either, so a half-width question fills the row there at any screen size, and the Questions tab says so where the widths are set. The stored width is left alone, so a page moved off either asks its questions paired again.

Note the Product List switch is read where the picker is decided, not only where the form is drawn. `CheckoutConfig::picksProducts()` gates the merchant's picker on `showProducts`, and `Page::offersProductChoice()` and `StoreOrderRequest::wasAskedToChoose()` both go through it. A picker left standing behind a hidden list compiles a rule demanding a choice the form never drew — every order on a live page refused for a box no customer can find. The picker itself is kept, so showing the list again restores the page the merchant configured. The view branches on `$showProducts` (handed over by `CheckoutShortcode`), never on the layout: hidden, it draws one `<input type="hidden" name="quantities[id]" value="1">` per Product carrying the line markers, so the summary totals the same way and the Capture records every Product once.

The Default Selection goes through the same gate and is read just as totally. A product ticked by default behind a hidden list is a tick nobody can see and nobody can untick; a product ticked by default that the page no longer sells is a form opening against something it cannot offer. Both are dropped on read rather than enforced, like every other unusable value in a Config. Neither goes in the fingerprint: which box opens ticked is configuration, not a figure handed over at the door, and fingerprinting it would reject every open form each time a merchant changed their mind (ADR-0010). The same is true of the order button's wording and the line beneath it — a merchant editing copy must never turn away an order somebody has half-typed.

## Validation is a bounded vocabulary, and never a rule a merchant wrote
There is no box anywhere — not on the Checkout tab, not in a stored Config — that takes a rule string or a regular expression of the merchant's. What a question will accept is a length, a bound, a switch, and a shape chosen from `FieldPattern`. That is the whole of it, and it is a deliberate refusal rather than a feature nobody got round to.

Two reasons, and both are about where the failure lands. A malformed rule does not surface in the admin as an error a merchant can act on; it surfaces as a conversion rate going to zero on a page that is spending money, discovered a day later. And an expression nobody reviewed runs on a public endpoint that has no session and a loose rate limit, against text a stranger posts — the merchant cannot test it against the traffic it will meet. So the vocabulary is fixed in front of a reviewer, every expression in it is a plain character class with no backtracking construct, and adding to it is a code change.

`FieldConstraints` resolves the merchant's figures **once**, in `effective()`, and `htmlFor()` and `rulesFor()` both read that. Do not add an attribute in one and a rule in the other: the property the whole thing exists for is that a customer is never blocked by their browser from typing something a capture would have taken, nor refused for a reason the form never showed. The same goes for a ceiling — `CheckoutFieldType::lengthCeiling()` is the one figure that becomes both `maxlength` and `max:`, which is why neither `controlHtml()` nor `answerRules()` states a length any more.

Two consequences worth knowing. A textarea has no HTML `pattern`, so a shape on one is checked at capture only; that asymmetry is allowed *because* it fails in the safe direction, and anything that made the browser stricter than the server would not be. And a built-in constrains nothing: its rules belong to the column waiting for the answer, a Config decides its wording and its two flags and no more (ADR-0006), so `CheckoutField::constraints()` returns `none()` unless the field is one the merchant authored.

Both halves of "refused twice" apply, and the silent half differs by which figure is wrong. A smallest above the largest is refused on the tab with a message and **dropped** on read — dropped rather than enforced, because the alternative is a form on a live page that cannot be submitted at all. A longest above the ceiling is refused on the tab and **capped** on read, because the ceiling is a real limit and the merchant's figure is only too generous.

## A stored Config is read totally, and a value is refused twice
Every `fromArray()` here drops what it cannot use rather than throwing: an unusable field, an option with no value, a colour that does not parse. A landing page answering paid traffic with a 500 costs more than one asking a merchant one question fewer, or drawn in the wrong blue, than they meant.

That means every refusal is made in two places — worded on the Checkout tab, where there is a merchant to tell, and silent in the Config, where there is not. Keep both. The tab is not the only route a Config gets written, and for style tokens the silent one is load-bearing: it is what stops a value in the database ending the declaration it is written into. Ask the domain object for the refusal (`StyleToken::refusal()`, `CustomCheckoutField::keyRefusal()`) so the two cannot disagree about what is allowed. The Look tab is the one place a token is worded — `Look::controls()` builds one control per `StyleToken` case, by kind — and there is no second caller, because nothing else asks about a token.

## The fingerprint covers what the courier collects, and adding to it is not free
`PricingFingerprint` is written into the rendered form and re-checked at Capture, and it holds the linked Product ids, their prices, and the Delivery Option amounts — nothing else. The asymmetry is the point (ADR-0007): collecting an amount the Customer never agreed to is a refused parcel and courier fees in both directions, while capturing against a form missing a colour change is nothing. Anything you put in it rejects the in-flight submissions of everyone mid-form on a Page that is spending money, so the test is whether the thing you are adding changes the figure handed over at the door — not whether it changed.

Two directions to get this wrong. A new *priced* thing (a discount, a surcharge, a second charge of any kind) must go in, or it reopens the defect for that figure. A new *configuration* thing must not, however tempting the "just fingerprint the Config" simplification looks — that version rejects every open form on every save of the Checkout tab.

Note what follows from Products being in it by id: soft-deleting one refuses the forms that offered it, rather than quietly selling the rest at a lower total than the visitor agreed to. `StoreOrderRequest::unofferedProducts()` and the quantity drop in `OrderCapture` still stand, but only for a hand-made post — the fingerprint reaches a stale form first.

`PricingFingerprint::for()` takes a Page, and everything reads the figures through it — the view is handed one, and `matches()` recomputes one — because the form and the check reading two different sources is exactly the drift it exists to prevent. Do not compute one from `$page->products` or the Delivery Options directly.

Note the two halves are fingerprinted differently on purpose. Products go in by id, sorted, so a reorder in the admin costs nothing. Delivery amounts go in by position, because with the labels left out there is nothing else tying an amount to the arrangement it belongs to — a bare set could not tell a reorder from the Merchant swapping 60 and 120 between "Inside Dhaka" and "Outside Dhaka", which is a repricing of both.

## The Checkout tab is one class per concern, and CheckoutTab owns the order
`Schemas/Checkout/` holds one class per concern — LayoutChoice, Products, Questions, DeliveryOptions, PaymentMethods, Words, Look — each returning its own component (`LayoutCards`, `Toggle`, `Repeater`, `Section`), never a list. The layout picker is `App\Filament\Forms\Components\LayoutCards`, Filament's `Radio` with descriptions plus a thumbnail slot per card (`thumbnails()`), drawn as a grid by `gp-layout-cards` in `forms.css`; a layout's picture is a static file under `public/images/checkout-layouts/`, named by `CheckoutLayout::thumbnail()`, and the slot stays empty until one lands. `CheckoutTab::make()` holds the arrangement and nothing else; PageForm knows only that the tab exists. Add a setting to the concern that owns it, not to PageForm.

One seam crosses a concern, deliberately. `LayoutChoice::selected()` is how anything reads the chosen layout — Questions asks it whether the arrangement pairs half-width questions rather than reading `checkout_config.layout` itself, so the tab and a stored Config cannot disagree. (The picker is no longer gated on the layout; it is gated on the Product List switch, which lives on the same tab as the picker.) Look shares nothing with Questions: a question row carries no appearance box, so there is no second place a token control is built.

**The arrangement is a nested tab per concern, and the nesting is the point.** Layout, Products, Questions, Delivery, Payment, Words and Look are `Tab`s inside a `Tabs` inside the Checkout tab, so one concern is on screen at a time — the Style Tokens in particular are reachable without scrolling past every question the merchant has ever authored. The tab is called Look, and its wording is the glossary's: Style Token, never theme, variable or field appearance. They stay *inside* Checkout rather than being promoted beside the Page tab, because a Checkout Config is one thing a Page decides. The inner `Tabs` is `contained(false)`: the tab it sits in is already a card, and a second border says nothing the two rows of tabs have not already said.

Order still carries an argument: Layout is met before Products because it is the largest decision on the tab, and within Products the Product List switch is met before the picker it gates, so a merchant meets the cause before the effect. Products contributes `listShown()`, `sold()`, `picker()` and `preTicked()` separately because a concern returns its own component and never a list, not because anything is interleaved between them.

Two consequences of tabbing to keep in mind. A validation error raised on a nested tab is as invisible as one on an outer tab, so anything cross-cutting still belongs on a field outside them (see `.ai/rules/resources.md`, and PageForm's publish-time linter on `status`). And a nested Tab with no `columns()` inherits its container's count rather than falling back to one — state it, as every other Tab and Section here does.

The Look section has no heading of its own, because the tab above it already says the word. That is a heading rule, not a labelling one: a `Repeater`'s `label()` names the control a merchant is filling in (`Fields` under Questions, `Delivery options` under Delivery) and stays, while a `Section` heading directly beneath a tab of the same name is a card announcing what the merchant has just clicked.

`PageAuthoringTest` pins the arrangement by walking the live edit form's schema rather than the rendered HTML: the nested labels in order, and that Page and Checkout are still the only outer tabs. The per-tab test asserts a setting's state path is **on** its tab before filling it, which is the half that has to be asserted — `fillForm()` writes Livewire state straight through and never touches tab membership, so a save-only test would pass just as well with all five concerns back on one scroll. `shows exactly the eleven style tokens on the look tab and none anywhere else` pins the set by walking the schema: the eleven paths in the enum's order on Look, and no `style_tokens` path on any other tab.

## A question row is one line, and everything about it is settled in a modal
The Questions repeater is a form builder's list: every row is its summary line and nothing else. Rows are `collapsed(shouldMakeComponentCollapsible: false)` — held shut with no toggle — and a row's child schema is `Questions::carried()`, one `Hidden` per part of a question (`built_in`, `key`, `label`, `type`, `width`, `enabled`, `required`, `placeholder`, `help`, `options`, `constraints`). Those mirrors exist because `Schema::getState()` prunes any key with no component, so a part with no `Hidden` would vanish at save. Nothing on a row is typed into; do not put a control back in a row.

The Edit item action (`extraItemActions`) opens `Questions::settings()` — four Sections in order: Question, Hint, Choices (visible only for a merchant's own dropdown or radio question), Answer rules (visible only for a merchant's own written or number question). It is filled from `getRawItemState()` and its validated `$data` is written back as the **whole** row through `rawState()`. That is why `type`, `enabled` and `required` are `disabled()->dehydrated()` for a built-in / phone: a control the modal holds shut must still be in `$data`, or the row comes back short and `summarise()` misreads the absence. "Add a question" is the same modal (`addAction()` with a schema) and appends the row as it closes — Filament's own add would leave a wordless line nothing can open. Choices and Answer rules are `visible()` without `dehydratedWhenHidden()` on purpose: the modal *replaces* the row, and a dropdown turned into a single line has no choices to keep. Choices and Answer rules are `visible()` without `dehydratedWhenHidden()` on purpose: the modal *replaces* the row, and a dropdown turned into a single line has no choices to keep.

Every refusal a question can earn is raised in the modal, on its own box: key shape and built-in clash via `CustomCheckoutField::keyRefusal()`, duplicate keys against `rowsOtherThan()` (the other rows' raw state, passed into `settings()` because the modal's `Get` cannot see the list), bounds via `FieldConstraints`. Rows carry no rules, so `fillForm()` straight onto `checkout_config.fields` bypasses the tab's refusals — the Config's silent second refusal is what stands then, and tests that want a refusal must drive `callAction('add'|'edit')`.

`Questions::summarise()` reads a row's raw state and is unchanged: it says wording, "Not asked", type, "Must be answered"/"Optional", width — switched off and not compulsory are separate things and it spends different words on each. The dim on a switched-off row is CSS: `forms.css` matches `:has([data-gp-question-asked='false'])`, the attribute is `Questions::ASKED_MARKER` on the row's Edit button (the one control every row has), its value the `enabled` flag as the row was drawn, and the row is redrawn as the modal closes. `PageAuthoringTest` pins the pair — move or rename either half and fix both.

## The rendered subtotal must already account for the Default Selection
The island does `retotal()` every form once on load, so a visitor whose scripts run never sees a stale figure. That is not licence to render the wrong one. The form is a real form with a real action so that a visitor whose scripts never run can still order, and for them the rendered bytes are the only figure there will ever be — the old `$picksProducts ? 0 : sum` was correct while a picker always opened on nothing, and with a Default Selection it prints a zero beside boxes that are visibly ticked.

So the subtotal is summed over the lines that open ticked, through `$opensTicked` — the same closure `@checked` uses on the box, written once at the top of the view. Two readings of the same list is how a figure and a tick come to disagree. Do not lean on the load-time `retotal()` to cover a server-rendered total that is wrong: the load-time call exists to reconcile a *restored* form (a browser refilling boxes on back-navigation), not to excuse the first paint.

## Every control the Default Selection reads has to be live, and the Product List switch comes first
`Products::preTicked()` builds its options from `$get('products')`, is drawn at all only while `$get('checkout_config.show_products')` is on, and holds itself shut on `picksProducts()`, which is that switch **and** `$get('checkout_config.product_picker')`. So three controls must stay `live()` — `Products::listShown()`, `Products::sold()` and `Products::picker()`. Drop any of them and a merchant links a product and finds no tick box for it, or switches the picker on and finds the list still greyed out, with nothing failing and no error to act on. `PageAuthoringTest` pins all three flags for that reason, and pins that the switch is the first state path on the Products tab: it is the cause the two controls beneath it are the effect of.

The switch hides the picker and the tick list rather than disabling them — a control about something that is not on the page is not one a merchant can act on — and both carry `dehydratedWhenHidden()`, because Filament drops a hidden field from the saved state otherwise (plain `dehydrated()` is not enough; see `.ai/rules/schemas-order-complete.md`). Without it, a merchant toggling the list off and saving would silently lose their picker and their ticks. `PageAuthoringTest` asserts `isHidden()` and `isDehydratedWhenHidden()` on both by walking the live schema of a page stored with the switch off. The switch's label is the sentence #84 asked for, and its helper text names the glossary's **Product List**; do not call it the panel, the cart or the summary anywhere on the tab.

`preTicked()` is `live()` for its own reason: the over-one warning in its helper text counts what is ticked, and a warning that only appears after a save is a warning about a decision already made. It offers no select-all, because ticking everything is the expensive case ADR-0010 wants chosen knowingly and a one-click button reaches it past the warning that fires at two.

While the list is shown and the picker is off it is `disabled()->dehydrated()` rather than hidden (the picker is on screen, so the ticks that follow it stay on screen too), and in both states the merchant's list survives a save that cannot honour it; `CheckoutConfig::opensTicked()` makes the refusal again on read. Its options come from the links as they stand in the form rather than from the saved Page, so linking and pre-ticking a product needs no save in between — and a tick naming a product the Page has stopped selling stays in the Config, because throwing it away here would lose it on any save made while that product sat in the bin.

## A whole-form failure is the island's child, not the form's, and paints its own ground
Errors split by kind. A refusal keyed to a field is written into that field's slot, inside its wrapper. Everything else — the server's `page` key, a key the form never drew, a 429, a dropped connection, a 500 — goes into `.gio-checkout-banner`, which sits **above the form as its sibling inside `.gio-checkout-card`**. That placement is the point: every layout's additive block arranges the form's children, so a banner inside the form would need a cell of its own in every two-column arrangement, and the one test pinning it runs on every layout. Do not move it back into the form to "keep the slots together"; the script looks slots up through `islandFor(form)` for exactly this reason. The `selected` slot is the one error slot still a direct child of the form; a layout that arranges the form's children has to place it.

The banner is the one place in the sheet that does not trust the page's colours: shown, it fills itself with the refusal red (`#b91c1c`, not a token) and writes in `#fff`. A dark page is the case where the text beside a box can be hard to read, and the sentence saying the whole order was turned away may not depend on the page's colours at all. The reload button appears **only** for the page-moved case (any 422 that lands in the banner); a connection or server failure offers none, because what the customer typed is still good and a reload would throw it away for nothing.

The refusal red (`#b91c1c`) is written in the sheet and is not a token: what a refusal is written in is not a merchant's to restyle, because the one moment it must be readable is the moment the order did not go through. The three failure wordings are constants at the top of the script, one per cause, pinned by `LandingPageTest`. Adding a fourth kind of failure means a fourth sentence, not a reuse.

## A layout's additive block is the one place the sheet outranks a merchant at two classes
Every rule in `CheckoutLayout::styleRules()` is `.gio-checkout-<layout> .gio-checkout-thing`, so it beats the base's one-class declaration by specificity rather than by order — unavoidable, since the block is what an arrangement differs by and it has to reach inside the root that names it.

That is a real cost to the promise the flat sheet makes: a merchant restyling `.gio-checkout-description` or `.gio-checkout-image` at one class now loses on a page arranged in a layout that has an opinion about it, and has to name an ancestor of their own to win. Accepted, and it is the ceiling: two classes, never three, never an id, never `!important` — `leaves the checkout losable to a merchant's own stylesheet` runs on every arrangement and pins the last two.

So keep a block to what the arrangement actually changes. A declaration that could sit in the base at one class belongs in the base, where the merchant still beats it.

## The root is the section, the card is the panel, and the design's figures are the base
The base sheet is the handoff README's Stacked (1a) in rem: `.gio-checkout` is the section the design paints behind the card — `--gio-background` (default the design's grey `#f7f8fa`; a merchant types `transparent` to let the page through) and the design's padding — and carries no border and no radius of its own. `.gio-checkout-card` is the one bordered panel, at `35rem`, filled from `--gio-surface`, square-cornered as the design draws every card and row; the banner and the form are its children. Sizes are rem, not em, so the design's pixels hold at the browser default and scale with a page's root size. What is bordered inside is what a thumb has to hit — the boxes a customer types into, the stepper, the product rows, the choice rows — all filled from `--gio-surface`. Only the inputs, the stepper and the pictures read `--gio-radius`; rows and the card stay square (the token's helper text says so). One hairline in the whole card, above the summary, read from `--gio-border`; sections are set apart by whitespace (`.gio-checkout-section + .gio-checkout-section`) and the product panel draws no rule beneath. The total still rules itself off inside the summary. Words meant to recede — help, a description, the line under the button — are coloured from `--gio-muted` rather than faded with opacity; the design's secondary ink (labels, summary rows) is `color-mix(in srgb, var(--gio-text) 35%, var(--gio-muted))`, derived from the two tokens rather than a third colour. The button's hover darkens `--gio-button-background` by a `color-mix()` rather than naming a second colour.

The chosen delivery row is `.gio-checkout-choice:has(:checked)` and takes the accent on its border and nothing heavier; the picked product is `.gio-checkout-product:has(:checked)` and takes the accent border plus a tint mixed from the accent and the surface. No ring, no shadow: the design has none ("No shadows"), and the one `box-shadow` in the sheet is the focus ring on `.gio-checkout-input:focus`, mixed from the accent. The tick reads the accent through `accent-color` on the root. A merchant may not type a `var()` into any colour, because a value naming another token is one the tab cannot show the effect of. `:has()` because the row *is* the label and the control sits inside it; a browser that cannot read it draws the row it always drew. That rule is at one class and one pseudo-class — do not answer a merchant's complaint about it by adding a second class.

**The numbered sections are the view's, the headlines are Stacked's.** The document is three `.gio-checkout-section`s — products, fields with the delivery choice beneath, payment — then the summary and the button, in that order for every layout (ADR-0015). A `<h3 class="gio-checkout-heading">` with its `.gio-checkout-number` badge is drawn at the top of a section only where `$layout->draws(WordSlot::…)`, and the badge is numbered by position as sections are drawn (`$sectionNumber`), never by the design's fixed three: the products may be hidden and the payment choice may not be drawn, and a customer never reads a "2" with no "1". The heading rules are in the base whatever the layout, so the sheet is the same bytes whichever words a page draws.

**Every product row draws a line total.** `.gio-checkout-line-total` (`data-gio-line-total`) is rendered at one of the product's price and refilled by `retotal()` from `lineAmount(line)` — the price at the current quantity, ticked or not — while `lineSubtotal(line)` still adds nothing for an unticked line. An unticked line's total fades (`.gio-checkout-pick:not(:checked) ~ .gio-checkout-line-total { opacity: .45 }`), as the design draws it; the stepper stays hidden as before.

The quantity's word "Quantity", the delivery legend and the payment legend are clipped from sight with `.gio-checkout-hidden-label` (the design draws none of them) and stay in the accessibility tree; do not `display: none` a label. The quantity is a real `type="number"` input with its `min`, `max` and `step`, flanked by two `type="button"` steppers that call `stepUp()`/`stepDown()` and nothing else. The bounds live on the input once and the buttons read them; a readout that cannot be typed into was rejected (#54) because the input's bounds are what keep the browser and the capture agreed on the maximum. The buttons are `aria-hidden` and untabbable on purpose — the spinbutton already has arrow keys and a name — and the native spinner is left alone as the stepper a customer whose script never runs still has.

## The Checkout Words are copy, and copy is neither a token nor a figure
`CheckoutWords` holds everything the island says that a merchant may reword: the `OrderButton` (wording and the line beneath it), the three totals labels, a long and a short label per `PaymentMethod`, and every layout-owned slot. A slot is a `WordSlot` case — stored flat under `words` by its value (`stacked_products_headline`, …), with its default, label and refusal on the case — and which layout owns it is `CheckoutLayout::wordSlots()`, the exhaustive match the view (`$layout->draws($slot)`) and the Words tab (`Words::ownedBy()`, one Section per `CheckoutLayout::owningWords()`, `visible()` while chosen and `dehydratedWhenHidden()` on the Section) both read. `CheckoutWords::slot()` answers for any slot whatever the layout; the view asks `draws()` first. Every value is `null` for the design's words — bilingual, Bangla first then English — and the defaults live on those two classes, not in the view, so the tab's placeholder and the island's bytes are the same sentence. `CheckoutWords::defaultPaymentLabel()` / `defaultShortPaymentLabel()` are exhaustive matches, so a new enum case has to be given its words before anything draws it. What a silent button says is the layout's: the view reads `$words->orderButton->forLayout($layout)`, which fills a null wording from `CheckoutLayout::defaultButtonWording()` (Stacked: `OrderButton::DEFAULT_WORDING.' · {total}'`, the design's total-on-the-button; Invoice will word it differently), and the Words tab's placeholder follows `LayoutChoice::selected()` the same way. A merchant's own wording stands on every layout. The button's wording may carry `{total}`: the view substitutes it at render from the same `$total` the summary prints, so a visitor whose scripts never run reads a figure and never a placeholder, and the template rides on the button as `data-gio-submit-wording` **only** when the wording names the total, so `retotal()` leaves a plain button alone. `retotal()` skips a disabled button on purpose — the button is saying "Placing your order…" and a retotal in flight must not talk over it.

Stored under `words` in the Config, and read totally: `order_button` once sat at the top level and `CheckoutConfig::wordsFromArray()` is the one place the old key is still read, so a Config written before the move keeps its words with no migration and the first save writes the new shape. Every word is refused twice like everything else in a Config — `OrderButton::wordingRefusal()`, `CheckoutWords::labelRefusal()` and the two payment-label refusals, worded on the Words tab through `RefusedBy::rule()` and silent in `fromArray()` — and blank is never refused, because blank is the merchant saying nothing. `CheckoutWords::kept()` / `lineRefusal()` / `textRefusal()` are the shared cleaning and wording; `OrderButton` reads through them. None of it is a Style Token: a sentence is not a custom property, and `StyleToken::ButtonText` already means the button's text *colour*.

The Words tab (`Schemas/Checkout/Words`) is three headed Sections in the order the customer meets them — Button, Totals, Payment — and the Payment section is one `Fieldset` per enum case, `visible()` only while the Payment tab lists that method (`PaymentMethods::listedMethods()`, the seam, with an empty list reading as Cash on Delivery the way `offeredMethods()` does) and `dehydratedWhenHidden()` on the Fieldset, so a label written for a method survives every save made while it is off the page. Layout-owned slots are added to this tab by the layout that draws them, as a Section shown only while that layout is chosen, never as a fourth shared section.

The summary's delivery row is labelled as a charge (`deliveryLabel()`, default "ডেলিভারি চার্জ / Delivery") and no longer after the arrangement: the arrangement's own name is on the radio where it is chosen, as the designs draw it, and the script no longer relabels the row. Which of a method's two labels the view draws is `CheckoutLayout::drawsShortPaymentLabels()` (Bento grid, Compact embed, Dark panel short; the rest long) — one branch in the view, never a second. The logo, where shown, sits after the words at the far end of the row, as the design's slot does.

Nothing in `words` is in the fingerprint, and `CheckoutCaptureTest` proves editing it refuses no in-flight submission. Do not "tidy" it in for consistency with the priced things beside it.

## The payment box lists switched-on methods plus what the page already lists, and a refusal is worded, not raised
`Schemas/Checkout/PaymentMethods::offered()` builds its options from `PaymentSettings::enabledMethods()` **plus** whatever the page's list already holds, so a method switched off in Settings stays in the box where the merchant put it and comes back into the checkout in that position when it is switched on again. Dropping it from the options would let a save silently shorten the stored list. A listed method the installation cannot offer is worded in the helper text with `PaymentSettings::refusal()` and never raised as a validation error: the refusal is Settings' to lift, and the Config's `offeredMethods()` already makes the silent half on read. The Select is `live()` so the wording follows the list as it is edited.

Where a Customer goes after Capture is `CheckoutController::sendOn()`, in one place for the checkout post and the Retry Page's post alike: the gateway's page where `PaymentStarter` could start a Payment, else the Order Complete Page unless `Order::isUnpaid()`, then the Retry Page. The Order Complete Page draws a settled Order only: `orderComplete()` redirects an Unpaid Order to the Retry Page rather than drawing a second branch. Both pages are addressed by order number, send no-store and noindex, and print the Order and never the Customer. `isUnpaid()` is "online method and no Paid Payment", and `isPaid()` is a query over the Order's Payments rather than a column — see `.ai/rules/payments.md` for what may mark one Paid.

A Capture's `payment_method` rule reads `CheckoutConfig::acceptedMethods()` — the page's raw list plus what it offers now — not `offeredMethods()`. A form was drawn from the page as it stood, so a method the installation has since switched off is one that form offered in good faith: it captures Unpaid and lands on the Retry Page. Only a name the page never listed is refused.

## A Delivery Option's detail line is copy: refused twice, outside the fingerprint, stored only when present
`DeliveryOption::detail` ("1–2 days") is the line drawn under the option's name. It is copy, not a figure: `PricingFingerprint` reads the amounts only, and `leaves the fingerprint alone when a delivery option's detail line changes` pins that editing it refuses no in-flight order. Do not add it to the fingerprint or to what an Order snapshots.

Refused twice like every Config value — `DeliveryOption::detailRefusal()` (one line, at most `DETAIL_MAX_LENGTH`) is worded on the Delivery tab through `RefusedBy::rule()` and made again silently in `fromArray()` via `CheckoutWords::kept()`, which drops the line and keeps the option. `toArray()` writes the `detail` key only when there is one, so a row saying nothing stores the shape every Page held before the line existed; tests asserting `deliveryOptionsToArray()` rely on that.

The tab's label is the glossary's "Detail line". The view draws it as a `display: block` span inside `.gio-checkout-choice-label`, written on the same *template* line as the name so a row with none emits the bytes it always did; `.gio-checkout-choice-detail` is one flat rule in the base sheet. Whether it is drawn at all is `CheckoutLayout::drawsDeliveryDetail()` — the roomy arrangements yes, the segmented ones (Split reversed, Bento grid, Compact embed, Chips) no — read by the view as a predicate; the line stays in the Config either way. `draws a delivery option's detail line only on a layout with room for it` pins all ten.
