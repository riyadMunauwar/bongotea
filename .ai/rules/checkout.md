# Checkout

## Styling is a token set, never a generated rule
The island's CSS is flat, single-class and prefixed so that a merchant's own stylesheet overrides it without raising specificity — that is a promise the product makes, not an accident of how the block was written. A generated `.gio-checkout-field-3 { … }` would be more specific than the hand-written rule beside it on the same page, so the style editor would start winning arguments it is supposed to lose.

So everything a merchant can restyle is a custom property in `StyleToken`, declared once on `.gio-checkout` and read by the rules that were already there. A field that differs redeclares a token on its own wrapper and the cascade confines it; nothing generates a selector, which is also why the emitted block is the same length on a checkout asking twenty questions as on one asking two. If you find yourself wanting a new rule to express an appearance setting, add a token instead — and if it cannot be a token, it is asking for CSS the merchant should write.

Four consequences worth knowing before editing the block.

**An inherited property has to be declared on the field wrapper as well as on the root.** `color`, `font-size` and `accent-color` inherit as *computed* values, so a wrapper redeclaring `--gio-text` cannot reach back and change what `.gio-checkout` already worked out — only a declaration on the wrapper itself reads what the wrapper carries. That repetition in `.gio-checkout-field` is load-bearing; delete it and per-field text colour and font size silently stop working, with nothing failing. A token whose property is *not* inherited (a border, a radius, a background) needs no such pairing, because the declaration that reads it already sits on a descendant.

**Sizes below the root are `em` against `--gio-font-size`**, so nothing between a size and the root may set a font size or it compounds — this is why the summary's size sits on `.gio-checkout-row` rather than on the container, and why the field wrapper's `font-size` is the root's own value rather than a second one.

**There is deliberately no separate padding control for inputs.** `--gio-input-size` is one scale driving padding and font size together, because a box sized up without its text is a box a customer cannot read back what they typed in. It covers the rows a customer picks from as well as the boxes they type in; they are all things a thumb has to hit.

**A field's overrides go in an inline `style` attribute, which does outrank a merchant's stylesheet — for those tokens only.** Accepted, because the alternative is the generated selector this whole rule exists to avoid, and it is narrow: the merchant still wins by setting the resolved property (`.gio-checkout-input { border-color: … }`), which is the control the promise above is actually about. Don't "fix" it by raising the checkout's own specificity to match.

## A fixed modifier class is not the generated rule the token set exists to avoid
The rule above says an appearance setting becomes a token rather than a rule. Two things are deliberately not tokens, and neither breaks it.

**A layout is a class on the root, and every layout adds to one shared sheet.** There are five — stacked, split, compact, summary-first, form-only — and the base is common to all of them. What differs is a small additive block emitted *only* when that layout is the one chosen (ADR-0009). Form-only remains the degenerate case: it differs by what the view draws, the product panel omitted rather than hidden, so `.gio-checkout-form-only` carries no declarations of its own and is a stable hook for a merchant's CSS.

`--gio-max-width` means one thing in all five: how wide the part the customer types into sits. Split reads it as the form column and derives the container from it, rather than widening the container and letting the token go slack — a merchant who set a narrow value then switched to split would otherwise get it honoured into two columns too narrow to use, and a token that quietly stops applying on one layout is the setting-with-no-error this file keeps warning about. Do not give the token a layout-dependent default to work around this; the set is sparse and filled at emission precisely so a merchant's value is the only value.

The rule this is most often confused with still stands, so read it before "simplifying" the emission back: **a layout may not carry a sheet of its own.** The block rides inside every cached page, so five copies of the base would charge every visitor five times for the one arrangement they are looking at. An additive block that appears only when it applies charges nobody — which is why `LandingPageTest` now pins two things where it used to pin one: the base is identical across all five, and a page contains no other layout's rules. A test asserting the emitted styles are byte-identical *between* layouts is the old invariant and was correct only while form-only added nothing; do not restore it.

**A field's width is a flat class too, and its breakpoint cannot be a token.** `.gio-checkout-field-half` is in the base sheet whether or not any question uses it, so pairing every question costs the same bytes as pairing none, and it beats `.gio-checkout-field` by order rather than by specificity — the same trade the quantity stepper makes. The two-column grid exists only inside the media query, which is the whole of "the collapse on a phone cannot be overridden": there is nothing to override, because no per-page value reaches it. A custom property cannot be read in a media-query prelude, so a per-page breakpoint would have to be a generated rule — the thing the token set exists not to do. Compact is the one layout that pairs nothing: its additive block drops the grid back to a single column, so a half-width question fills the row there at any screen size. The stored width is left alone, so a page moved off compact asks its questions paired again.

Note the layout is read where the picker is decided, not only where the form is drawn. `CheckoutConfig::picksProducts()` gates the merchant's switch on the layout, and `Page::offersProductChoice()` and `StoreOrderRequest::wasAskedToChoose()` both go through it. A picker left standing on a form-only page compiles a rule demanding a choice the form never drew — every order on a live page refused for a box no customer can find. The switch itself is kept, so switching back restores the page the merchant configured.

The Default Selection goes through the same gate and is read just as totally. A product ticked by default on a layout that draws no products is a tick nobody can see and nobody can untick; a product ticked by default that the page no longer sells is a form opening against something it cannot offer. Both are dropped on read rather than enforced, like every other unusable value in a Config. Neither goes in the fingerprint: which box opens ticked is configuration, not a figure handed over at the door, and fingerprinting it would reject every open form each time a merchant changed their mind (ADR-0010). The same is true of the order button's wording and the line beneath it — a merchant editing copy must never turn away an order somebody has half-typed.

## Validation is a bounded vocabulary, and never a rule a merchant wrote
There is no box anywhere — not on the Checkout tab, not in a stored Config — that takes a rule string or a regular expression of the merchant's. What a question will accept is a length, a bound, a switch, and a shape chosen from `FieldPattern`. That is the whole of it, and it is a deliberate refusal rather than a feature nobody got round to.

Two reasons, and both are about where the failure lands. A malformed rule does not surface in the admin as an error a merchant can act on; it surfaces as a conversion rate going to zero on a page that is spending money, discovered a day later. And an expression nobody reviewed runs on a public endpoint that has no session and a loose rate limit, against text a stranger posts — the merchant cannot test it against the traffic it will meet. So the vocabulary is fixed in front of a reviewer, every expression in it is a plain character class with no backtracking construct, and adding to it is a code change.

`FieldConstraints` resolves the merchant's figures **once**, in `effective()`, and `htmlFor()` and `rulesFor()` both read that. Do not add an attribute in one and a rule in the other: the property the whole thing exists for is that a customer is never blocked by their browser from typing something a capture would have taken, nor refused for a reason the form never showed. The same goes for a ceiling — `CheckoutFieldType::lengthCeiling()` is the one figure that becomes both `maxlength` and `max:`, which is why neither `controlHtml()` nor `answerRules()` states a length any more.

Two consequences worth knowing. A textarea has no HTML `pattern`, so a shape on one is checked at capture only; that asymmetry is allowed *because* it fails in the safe direction, and anything that made the browser stricter than the server would not be. And a built-in constrains nothing: its rules belong to the column waiting for the answer, a Config decides its wording and its two flags and no more (ADR-0006), so `CheckoutField::constraints()` returns `none()` unless the field is one the merchant authored.

Both halves of "refused twice" apply, and the silent half differs by which figure is wrong. A smallest above the largest is refused on the tab with a message and **dropped** on read — dropped rather than enforced, because the alternative is a form on a live page that cannot be submitted at all. A longest above the ceiling is refused on the tab and **capped** on read, because the ceiling is a real limit and the merchant's figure is only too generous.

## A stored Config is read totally, and a value is refused twice
Every `fromArray()` here drops what it cannot use rather than throwing: an unusable field, an option with no value, a colour that does not parse. A landing page answering paid traffic with a 500 costs more than one asking a merchant one question fewer, or drawn in the wrong blue, than they meant.

That means every refusal is made in two places — worded on the Checkout tab, where there is a merchant to tell, and silent in the Config, where there is not. Keep both. The tab is not the only route a Config gets written, and for style tokens the silent one is load-bearing: it is what stops a value in the database ending the declaration it is written into. Ask the domain object for the refusal (`StyleToken::refusal()`, `CustomCheckoutField::keyRefusal()`) so the two cannot disagree about what is allowed.

## The fingerprint covers what the courier collects, and adding to it is not free
`PricingFingerprint` is written into the rendered form and re-checked at Capture, and it holds the linked Product ids, their prices, and the Delivery Option amounts — nothing else. The asymmetry is the point (ADR-0007): collecting an amount the Customer never agreed to is a refused parcel and courier fees in both directions, while capturing against a form missing a colour change is nothing. Anything you put in it rejects the in-flight submissions of everyone mid-form on a Page that is spending money, so the test is whether the thing you are adding changes the figure handed over at the door — not whether it changed.

Two directions to get this wrong. A new *priced* thing (a discount, a surcharge, a second charge of any kind) must go in, or it reopens the defect for that figure. A new *configuration* thing must not, however tempting the "just fingerprint the Config" simplification looks — that version rejects every open form on every save of the Checkout tab.

Note what follows from Products being in it by id: soft-deleting one refuses the forms that offered it, rather than quietly selling the rest at a lower total than the visitor agreed to. `StoreOrderRequest::unofferedProducts()` and the quantity drop in `OrderCapture` still stand, but only for a hand-made post — the fingerprint reaches a stale form first.

`PricingFingerprint::for()` takes a Page, and everything reads the figures through it — the view is handed one, and `matches()` recomputes one — because the form and the check reading two different sources is exactly the drift it exists to prevent. Do not compute one from `$page->products` or the Delivery Options directly.

Note the two halves are fingerprinted differently on purpose. Products go in by id, sorted, so a reorder in the admin costs nothing. Delivery amounts go in by position, because with the labels left out there is nothing else tying an amount to the arrangement it belongs to — a bare set could not tell a reorder from the Merchant swapping 60 and 120 between "Inside Dhaka" and "Outside Dhaka", which is a repricing of both.

## The Checkout tab is one class per concern, and CheckoutTab owns the order
`Schemas/Checkout/` holds one class per concern — LayoutChoice, Products, Questions, DeliveryOptions, PaymentMethods, Appearance — each returning its own component (`Select`, `Toggle`, `Repeater`, `Section`), never a list. `CheckoutTab::make()` holds the arrangement and nothing else; PageForm knows only that the tab exists. Add a setting to the concern that owns it, not to PageForm.

Two seams cross a concern, both deliberate. `LayoutChoice::selected()` is how anything reads the chosen layout — Products gates the picker on it rather than reading `checkout_config.layout` itself, so the tab and a stored Config cannot disagree. `Appearance::controls()` builds the token controls for both the checkout-wide section and the per-question override section inside a Questions row; the row's own section stays in Questions, because what is being restyled there is the question.

**The arrangement is a nested tab per concern, and the nesting is the point.** Layout, Products, Questions, Delivery, Payment and Appearance are `Tab`s inside a `Tabs` inside the Checkout tab, so one concern is on screen at a time — the checkout-wide appearance controls in particular are reachable without scrolling past every question the merchant has ever authored. They stay *inside* Checkout rather than being promoted beside the Page tab, because a Checkout Config is one thing a Page decides. The inner `Tabs` is `contained(false)`: the tab it sits in is already a card, and a second border says nothing the two rows of tabs have not already said.

Order still carries the argument the flat tab made: Layout is met before Products because it gates whether the picker can be asked about at all, so a merchant meets the cause before the effect. That is now a tab before a tab rather than a control between two controls — Products still contributes `sold()` and `picker()` separately because a concern returns its own component and never a list, not because anything is interleaved between them.

Two consequences of tabbing to keep in mind. A validation error raised on a nested tab is as invisible as one on an outer tab, so anything cross-cutting still belongs on a field outside them (see `.ai/rules/resources.md`, and PageForm's publish-time linter on `status`). And a nested Tab with no `columns()` inherits its container's count rather than falling back to one — state it, as every other Tab and Section here does.

The Appearance section lost its own heading in the move, because the tab above it now says the word. That is a heading rule, not a labelling one: a `Repeater`'s `label()` names the control a merchant is filling in (`Fields` under Questions, `Delivery options` under Delivery) and stays, while a `Section` heading directly beneath a tab of the same name is a card announcing what the merchant has just clicked.

`PageAuthoringTest` pins the arrangement by walking the live edit form's schema rather than the rendered HTML: the nested labels in order, and that Page and Checkout are still the only outer tabs. The per-tab test asserts a setting's state path is **on** its tab before filling it, which is the half that has to be asserted — `fillForm()` writes Livewire state straight through and never touches tab membership, so a save-only test would pass just as well with all five concerns back on one scroll.

## A collapsed question row is all a merchant reads, so the row must be whole
The Questions repeater opens `collapsed()`, so a checkout asking ten questions is ten lines to scan and reorder rather than a page to scroll. `Questions::summarise()` is what a merchant then picks a question by, and it reads the row's Livewire state through `getStateSnapshot()` — which runs dehydration, so **a control the tab holds shut is dropped from what the summary reads**. That is why `enabled`, `required` and `type` are all `disabled()->dehydrated()`: left dropped, phone's two forced flags vanish and the row calls the one question a Checkout may never stop asking for optional. Every control the summary reads that a merchant can change must also be live — `enabled`, `required`, `type` and `width` are `live()`, `label` is `live(onBlur: true)` — or the line lies until the next save. (`built_in` needs nothing: it is a `Hidden` the Config writes and the merchant cannot touch.) Its wording comes from `CheckoutFieldType::label()` and `FieldWidth::label()`, which are also what the pickers inside the row are built from, so a summary cannot call a question something the control below it does not.

Switched off and not compulsory are separate things, and the summary says both in different words. A switched-off question keeps whatever the merchant configured behind it, so a row can truthfully be "Not asked" and "Must be answered" at once — and a merchant reading one word for both would switch a question on to find a box they cannot get past.

The dim on a switched-off row is CSS rather than markup, because `itemLabel()` is escaped text and there is no per-item class hook. `forms.css` finds the row with `:has([data-gp-question-asked][aria-checked='false'])`; the attribute is `Questions::ASKED_MARKER`, it is on that one toggle, and `aria-checked` is what Alpine keeps in step with the switch so the row dims as it is thrown. Nothing in the rendered HTML says which rule matched, so `PageAuthoringTest` pins the pair — move or rename either half and fix both.

Adding a question stays one click: Filament's own add action calls `collapsed(false)` on the **component** for that request, so every row it draws afresh draws open. Only the new one is drawn afresh — the others carry `wire:key` and `wire:ignore.self`, so Livewire morphs them and Alpine never re-runs their `x-data`. Do not reach for a closure to reproduce this; note the test asserts the component's flag, because that flag is the whole of what the server decides.

One difference from the Section warning in `.ai/rules/resources.md`: a repeater *item* does reveal itself on a failed save, because Filament walks up from the first `[data-validation-error]` dispatching `expand` and the item listens for it. The `Answers` and `Appearance` sections inside a row do not, so that warning still stands for them — and only the first errored row opens, not every one.

## The rendered subtotal must already account for the Default Selection
The island does `retotal()` every form once on load, so a visitor whose scripts run never sees a stale figure. That is not licence to render the wrong one. The form is a real form with a real action so that a visitor whose scripts never run can still order, and for them the rendered bytes are the only figure there will ever be — the old `$picksProducts ? 0 : sum` was correct while a picker always opened on nothing, and with a Default Selection it prints a zero beside boxes that are visibly ticked.

So the subtotal is summed over the lines that open ticked, through `$opensTicked` — the same closure `@checked` uses on the box, written once at the top of the view. Two readings of the same list is how a figure and a tick come to disagree. Do not lean on the load-time `retotal()` to cover a server-rendered total that is wrong: the load-time call exists to reconcile a *restored* form (a browser refilling boxes on back-navigation), not to excuse the first paint.

## Every control the Default Selection reads has to be live, including the one on another tab
`Products::preTicked()` builds its options from `$get('products')` and holds itself shut on `picksProducts()`, which is `$get('checkout_config.product_picker')` **and** `LayoutChoice::selected($get)`. So three controls must stay `live()` — `Products::sold()`, `Products::picker()` and `LayoutChoice::control()`, the last of them on a different tab, which is the one a refactor is most likely to drop. Drop any of them and a merchant links a product and finds no tick box for it, or switches the picker on and finds the list still greyed out, with nothing failing and no error to act on. `PageAuthoringTest` pins all three flags for that reason.

`preTicked()` is `live()` for its own reason: the over-one warning in its helper text counts what is ticked, and a warning that only appears after a save is a warning about a decision already made. It offers no select-all, because ticking everything is the expensive case ADR-0010 wants chosen knowingly and a one-click button reaches it past the warning that fires at two.

It follows the picker in being `disabled()->dehydrated()` rather than hidden, for the same reason: the merchant's list survives a layout or a switch that cannot honour it, and `CheckoutConfig::opensTicked()` makes the refusal again on read. Its options come from the links as they stand in the form rather than from the saved Page, so linking and pre-ticking a product needs no save in between — and a tick naming a product the Page has stopped selling stays in the Config, because throwing it away here would lose it on any save made while that product sat in the bin.

## A whole-form failure is the island's child, not the form's, and paints its own ground
Errors split by kind. A refusal keyed to a field is written into that field's slot, inside its wrapper. Everything else — the server's `page` key, a key the form never drew, a 429, a dropped connection, a 500 — goes into `.gio-checkout-banner`, which sits **above the form as a child of `.gio-checkout`**. That placement is the point: every layout's additive block arranges the form's children, so a banner inside the form would need a grid cell in split and an `order` in summary-first, and the one test pinning it runs on all five layouts. Do not move it back into the form to "keep the slots together"; the script looks slots up through `islandFor(form)` for exactly this reason. The `selected` slot is the one error slot still a direct child of the form, and the split rule placing `.gio-checkout-error` in column 1 exists for it.

The banner is the one place in the sheet that does not trust the page's colours: shown, it fills itself with `--gio-error` and writes in `#fff`. A dark page with the default red is the case where the text beside a box is invisible until the merchant lightens the token, and the sentence saying the whole order was turned away may not wait for that. The reload button appears **only** for the page-moved case (any 422 that lands in the banner); a connection or server failure offers none, because what the customer typed is still good and a reload would throw it away for nothing.

`--gio-error` is a token like the rest — refused on the tab by `StyleToken::refusal()`, dropped on read by `StyleTokens::fromArray()`, one field may override it — and the three failure wordings are constants at the top of the script, one per cause, pinned by `LandingPageTest`. Adding a fourth kind of failure means a fourth sentence, not a reuse.

## A layout's additive block is the one place the sheet outranks a merchant at two classes
Every rule in `CheckoutLayout::styleRules()` is `.gio-checkout-<layout> .gio-checkout-thing`, so it beats the base's one-class declaration by specificity rather than by order — unavoidable, since the block is what an arrangement differs by and it has to reach inside the root that names it.

That is a real cost to the promise the flat sheet makes: a merchant restyling `.gio-checkout-description` or `.gio-checkout-image` at one class now loses on a page arranged in a layout that has an opinion about it, and has to name an ancestor of their own to win. Accepted, and it is the ceiling: two classes, never three, never an id, never `!important` — `leaves the checkout losable to a merchant's own stylesheet` runs on every arrangement and pins the last two.

So keep a block to what the arrangement actually changes. A declaration that could sit in the base at one class belongs in the base, where the merchant still beats it.

## The island draws no panel, and the split arithmetic reads the root's edges
The root carries no border, no padding and no radius. It sits inside a Page the merchant already designed, so a box of its own would double-frame whatever they drew around it; a merchant who wants the panel adds it in their own stylesheet, which is what the flat single-class sheet exists to allow. What is bordered is what a thumb has to hit — the boxes a customer types into, the stepper, the product rows, the delivery rows — and sections are set apart by one hairline each: beneath the products and above the summary, both read from `--gio-border` and `--gio-border-width`, so the existing tokens restyle the whole island.

Two consequences. `CheckoutLayout::SPLIT_RULES` reserves around the form column exactly what the track takes back out (eighteen rem, and no border term), *because* the root has no edges; a padding or border put back on `.gio-checkout` has to be added to what the container reserves or the form column comes out narrower than the merchant's figure by that much — `reserves around a split checkout's form column exactly what it takes back out` reads all three figures for this reason. And any layout that puts the summary directly beneath the products (split, summary-first) has to drop the panel's bottom rule, or the base's two hairlines meet as a double line; `draws one rule between the products and the total wherever the two meet` pins both.

The total carries a third hairline, and it is not a section rule. `.gio-checkout-total` rules itself off from the summary lines above it, inside the summary, so a layout that drops the panel's bottom rule to avoid a double line (split, summary-first) must leave it alone — it never meets another rule. Compact does restate its margin and padding, because compact's two-class `.gio-checkout-row` rule would otherwise squeeze the total against the line before it; a layout that tightens the summary's rows has to restate the total's spacing as well, or the two-class row rule wins and the total loses its air.

The chosen delivery row is `.gio-checkout-choice:has(:checked)` and the picked product is `.gio-checkout-product:has(:checked)`; both are painted — border, one-pixel ring, and a `color-mix()` tint of the ground — from `--gio-selected` and nothing else, and the tick reads it too through `accent-color` on the root and the field wrapper. The token's *default* is `var(--gio-accent)` rather than a colour, which is how an unset token follows the accent and an already-published page looks unchanged; do not replace that with today's blue, and do not let a merchant type a `var()` (the colour refusal turns it away, because a value naming another token is one the tab cannot show the effect of). One trap worth knowing: a wrapper inherits the root's already-*resolved* `--gio-selected`, so a question redeclaring only its accent would keep its focus ring and lose its ticks. `StyleTokens::declarations()` closes that by restating `--gio-selected: var(--gio-accent)` on any sparse set that carries an accent and no selected colour — which is why a question styled with only an accent emits two declarations, and why `keeps a question's ticks in the accent that question was given` pins both shapes. `:has()` because the row *is* the label and the control sits inside it, so there is no sibling to reach the way the quantity stepper does; a browser that cannot read it draws the row it always drew, with the radio still saying which is picked. That rule is at one class and one pseudo-class, the same weight as `.gio-checkout-input:focus` — do not answer a merchant's complaint about it by adding a second class.

The quantity is a real `type="number"` input with its `min`, `max` and `step`, flanked by two `type="button"` steppers that call `stepUp()`/`stepDown()` and nothing else. The bounds live on the input once and the buttons read them; a readout that cannot be typed into was rejected (#54) because the input's bounds are what keep the browser and the capture agreed on the maximum. The buttons are `aria-hidden` and untabbable on purpose — the spinbutton already has arrow keys and a name — and the native spinner is left alone as the stepper a customer whose script never runs still has.

## The order button's words are copy, and copy is neither a token nor a figure
`OrderButton` holds what the button says and the line beneath it, `null` for either meaning the words it has always carried — the defaults live on that class, not in the view, so the tab's placeholder and the island's bytes are the same sentence. The wording may carry `{total}`: the view substitutes it at render from the same `$total` the summary prints, so a visitor whose scripts never run reads a figure and never a placeholder, and the template rides on the button as `data-gio-submit-wording` **only** when the wording names the total, so `retotal()` leaves a plain button alone. `retotal()` skips a disabled button on purpose — the button is saying "Placing your order…" and a retotal in flight must not talk over it.

It is refused twice like everything else in a Config — `OrderButton::wordingRefusal()` / `noteRefusal()` worded on the tab by `Schemas/Checkout/OrderButtonCopy`, silent in `fromArray()` — and blank is never refused, because blank is the merchant saying nothing. It is not a Style Token: a sentence is not a custom property, and `StyleToken::ButtonText` already means the button's text *colour*. It sits on the Appearance tab as a headed Section beneath the token section rather than as a sixth nested tab, because two boxes are not a concern of their own; the Section keeps its heading, unlike the token section, because it is not the whole of what the tab is headed with.

Neither value is in the fingerprint, and `CheckoutCaptureTest` proves editing them refuses no in-flight submission. Do not "tidy" it in for consistency with the priced things beside it.

## The payment box lists switched-on methods plus what the page already lists, and a refusal is worded, not raised
`Schemas/Checkout/PaymentMethods::offered()` builds its options from `PaymentSettings::enabledMethods()` **plus** whatever the page's list already holds, so a method switched off in Settings stays in the box where the merchant put it and comes back into the checkout in that position when it is switched on again. Dropping it from the options would let a save silently shorten the stored list. A listed method the installation cannot offer is worded in the helper text with `PaymentSettings::refusal()` and never raised as a validation error: the refusal is Settings' to lift, and the Config's `offeredMethods()` already makes the silent half on read. The Select is `live()` so the wording follows the list as it is edited.

Where a Customer goes after Capture is `CheckoutController::sendOn()`, in one place for the checkout post and the Retry Page's post alike: the gateway's page where `PaymentStarter` could start a Payment, else the Order Complete Page unless `Order::isUnpaid()`, then the Retry Page. The Order Complete Page draws a settled Order only: `orderComplete()` redirects an Unpaid Order to the Retry Page rather than drawing a second branch. Both pages are addressed by order number, send no-store and noindex, and print the Order and never the Customer. `isUnpaid()` is "online method and no Paid Payment", and `isPaid()` is a query over the Order's Payments rather than a column — see `.ai/rules/payments.md` for what may mark one Paid.

A Capture's `payment_method` rule reads `CheckoutConfig::acceptedMethods()` — the page's raw list plus what it offers now — not `offeredMethods()`. A form was drawn from the page as it stood, so a method the installation has since switched off is one that form offered in good faith: it captures Unpaid and lands on the Retry Page. Only a name the page never listed is refused.
